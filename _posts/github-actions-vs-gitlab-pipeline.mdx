It's been almost 5 years since my last post. Time for a new one 😅

Developers[1](#fn-1) spend a lot of time with source control systems like GitHub and GitLab.
I would rate the choice of these systems as one of the most important decisions a development team can make.
I have many times seen choices being made based on simplistic criteria like it is open source and free to host.
I want to take a more holistic view and try to reason about the overall system design.

In this first post, I want to focus only on the CI/CD pipelines provided by GitHub vs GitLab and what
choices we are making with each choice. I want to make a second post that will focus on the other features
of these systems like communication using issue tracking, ability to build custom solutions on top of apis,
granular permissions for these apis, securely integrating with other systems
(CI taking to cloud provider with OIDC), etc. ...hopefully soon 😁

## Github Actions

Let us look at a simple workflow yaml for Github Action. I have used a terraform project as an example.

```yaml title="github-actions.yaml"
on:
  push:
    paths:
      - 'terraform/*.tf'
    branches:
      - main

permissions:
  contents: read
  id-token: write
  pull-requests: write

jobs:
  terraform:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: hashicorp/setup-terraform@v4
        with:
          terraform_version: '1.14.6'

      - uses: 'google-github-actions/auth@v3'
        with:
          project_id: 'my-project'
          workload_identity_provider: 'projects/123456789/locations/global/workloadIdentityPools/my-pool/providers/my-provider'

      - name: Terraform Init
        working-directory: ./infra
        run: terraform init
```

Let's take this yaml apart and reason about the design choices.

The `on` section is a declarative way to specify the events that will trigger this workflow.
It further allows us to filter the events based on the branch and the files that have changed —
again declarative, i.e. we specify the what and not the how. It also means that as long
as we create a push event, the workflow will be triggered. This event can be created from a slack
channel or a bot.

`permissions` section is a declarative way to specify the permissions that this workflow will have.
It decouples permissions from the jobs that will run. For example, the job can update the pull
request with the output of terraform plan because we asked for write permissions.
We can also reason from the yaml that the permissions are scoped to the workflow and
not the user who triggered the workflow. So a github app with admin rights or a slack message triggering
the workflow gets the same permissions.

The `jobs` and `steps` sections describe the work. Jobs run in parallel on runners, steps run
in sequence inside a job. What is worth reasoning about is what steps share — they share a
workspace filesystem, and that is it. No shared memory, no shared process, no shared runtime.
This is a deliberately weak coupling between steps, and it is what makes composition safe.
Any step can be swapped for any other step and the rest of the job does not need to know.

The `uses` keyword is where composition actually happens, and it is telling us something
specific about the system. `hashicorp/setup-terraform@v4` is not a marketplace entry — it is
a reference to a github repository pinned to a git tag. There is no separate registry, no
approval process, no publish step. Anyone with a public repo and an `action.yaml` has
extended the system, and anyone can `uses:` it. The consequence is that the barrier to
extending Github Actions is essentially zero, and forking or vendoring a stale action is
a legitimate answer because the substrate underneath is just git.

The deeper property visible from this yaml is that everything it describes also exists
as an API. `push` is a git event, `workflow_dispatch` is an api call, `permissions` is a
scope on a short-lived token, artifacts are objects with urls. The yaml is one client of
the system, not the system itself. So we can trigger a workflow from a slack bot, rerun
a failed job from a dashboard, gate a deploy from a security scanner, or write our own UI
on top. Any tooling we want, we can build.

## Gitlab Pipeline

Here is roughly the same pipeline in Gitlab[2](#fn-2).

```yaml title="gitlab-ci.yaml"
image: hashicorp/terraform:1.14.6

stages:
  - terraform

terraform:
  stage: terraform
  id_tokens:
    GCP_ID_TOKEN:
      aud: 'https://iam.googleapis.com/projects/123456789/locations/global/workloadIdentityPools/my-pool/providers/my-provider'
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      changes:
        - terraform/*.tf
  script:
    - cd infra
    - terraform init
```

The first thing to notice is that Gitlab (the product offering hosted git) is
tightly coupled with the pipeline. This is because nothing in the pipeline
yaml is a reference to an event or an api call.

`image` at the top is a more closed construct. It is telling us the environment for a
Gitlab job is a container, and the container is the unit of reuse. Everything the
job does is bound to the
base image, and two tools that need different environments mean two jobs. Reuse of an
environment does not compose with reuse of a step — we pick one image per job and it
defines the world for that job.

I also think using container images as the unit of sandboxing is a wrong abstraction.
It is very cheap to create VMs **today** and run jobs in them.
This skips the complexity of processes talking to each other when testing and
running out of memory and cpu.

The decoupling between `stages` and `jobs` is a nice design choice. It allows us to
express more complex workflows where we can promote between stages with ease. For example —

```yaml
deploy:staging:
  stage: deploy

deploy:prod:
  stage: deploy
```

The api story is different too. Gitlab has an api and it is a good one, but the pipeline
is more of a closed object. The yaml, the templates, the images, the registry, the
environments all sit inside Gitlab. It composes very well with other Gitlab primitives
and less well with things outside that boundary. Extensibility here means adopting more
of the product, not building whatever we want on top of it.

## Closing thoughts

The two yamls describe two different design philosophies. GitHub's is a thin declarative
facade over the functionality GitHub offers and their REST apis.
The yaml exists inside a larger system that allows for an open marketplace. This means it is easy
to build custom tooling, integrate third-party vendors, or let non-CI actors participate in the
pipeline.

Gitlab's yaml describes an integrated product where composition, environments, and templates all live inside the
pipeline definition itself. In some sense, this is like
the Apple ecosystem — it is a closed system that is easy to use and hard to extend.

Neither is wrong, but they lead to very different systems.
